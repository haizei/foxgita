# 图片计划 Recipe 加速规格

**日期：** 2026-09-26

**状态：** 已确认，待开发

**范围：** 现场拍照与相册选图到可编辑 Practice Draft 的端到端加速

**关联能力：** `practice.plan.from_image`、MessagesRuntime、Artifact 校验、Host Approval

## Problem Statement

用户通过现场拍照或相册选择图片生成练习时，等待时间过长，而且当前进度不能准确反映系统正在处理的阶段。现场拍照会先把原始高清图片编码成高质量 JPEG，随后图片计划 Recipe 又解码、缩放并再次编码；后一次处理还可能占用主线程。处理后的图片以 Base64 嵌入完整 JSON 请求，客户端等待模型返回完整响应后才进入 Artifact 校验和预览。用户看到的是模拟进度，无法判断慢在图片处理、上传、模型还是校验，也无法获得及时、可信的反馈。

现有 Invocation 耗时从 Recipe Runner 内部开始，未覆盖相机编码、相册资源加载、图片准备和队列等待，因此开发者看到的调用耗时短于用户实际等待时间。Provider能力也没有显式建模：未知接口可能先携带不支持的 JSON 格式参数失败，再发起兼容请求，额外增加网络往返和模型费用。

用户需要更快、更稳定、可取消且可解释的图片计划生成体验；团队需要可以定位每个阶段耗时、验证图片压缩没有损害识别质量，并在指标不达标时安全回滚。

## Solution

建立一条由拍照和相册共享的图片计划生成管线。图片来源只解码一次，所有缩放、文字区域检测和 JPEG 编码都在后台完成，形成不会持久化的会话级派生图片。标准输入使用最长边1024的图片；检测到密集小字时使用1280高清可读模式。单张目标不超过1MB，三张合计目标不超过2.5MB；超限时在质量下限内逐步压缩，仍无法满足时请求用户减少图片或重新拍摄。

生成页面使用真实阶段而不是模拟百分比：优化图片、上传并请求识别、AI生成练习计划、检查结果。支持流式的Provider由 MessagesRuntime接收SSE事件，以首事件改善反馈，但局部JSON不会渲染；只有完整响应通过Artifact与领域校验后，才展示可编辑Practice Draft。未知Provider使用保守能力配置，不通过试错请求探测，也不进行可能产生额外费用的隐形自动重试。

Schema V19为Invocation增加可选的阶段耗时和载荷指标，覆盖从用户开始生成到预览完成的端到端等待。新图片管线和Runtime流式能力分别受独立功能开关控制，通过固定质量评测集和分阶段灰度发布。

## User Stories

1. As a 吉他学习者, I want 拍照后快速进入生成状态, so that 我知道操作已经生效而不是怀疑应用卡住。
2. As a 吉他学习者, I want 单张照片通常在6秒内生成可编辑草稿, so that AI不会打断我的练习节奏。
3. As a 吉他学习者, I want 生成过程保持界面流畅, so that 我可以阅读状态、取消任务或返回上一页。
4. As a 吉他学习者, I want 看到系统正在优化图片、等待AI还是检查结果, so that 我能理解等待发生在哪里。
5. As a 吉他学习者, I want 超过正常等待时间时得到明确提示, so that 我不会被停在90%的假进度上。
6. As a 吉他学习者, I want 随时取消尚未完成的生成, so that 我不会为不再需要的请求继续等待或付费。
7. As a 吉他学习者, I want 取消后不会创建练习, so that AI不会产生意外业务写入。
8. As a 吉他学习者, I want 重新生成时复用当前会话已经准备好的图片, so that 相同图片不会重复压缩并延长等待。
9. As a 吉他学习者, I want 关闭页面后派生图片立即释放, so that 私人照片不会因为加速而被长期保存。
10. As a 吉他学习者, I want 模糊、倾斜或文字太小的照片在请求前得到重拍建议, so that 我不会等待很久才得到不可靠计划。
11. As a 吉他学习者, I want 边界清晰度问题由我决定是否使用高清重试, so that 应用不会隐形增加模型调用和费用。
12. As a 吉他学习者, I want 图片计划先进入可编辑预览, so that 我可以检查标题、时长和步骤再加入今日练习。
13. As a 吉他学习者, I want 未通过结构或领域校验的模型内容不被展示, so that 我不会看到残缺或不可信的计划。
14. As a 吉他学习者, I want 相册中的一至三张图片和现场拍照使用一致流程, so that 两个入口具有相同的速度、安全和预览行为。
15. As a 吉他学习者, I want 三张图片生成时仍有明确的等待预期, so that 我可以决定是否减少图片换取速度。
16. As a 使用自定义AI接口的用户, I want 应用只启用接口明确支持的能力, so that 不兼容参数不会让每次生成先失败一次。
17. As a 使用不支持流式接口的用户, I want 仍能正常生成图片计划, so that 流式能力不是使用Recipe的前提。
18. As a 使用支持流式接口的用户, I want 模型开始返回时立即看到真实状态变化, so that 首次响应不会被完整JSON等待掩盖。
19. As a 注重隐私的用户, I want 原图、派生图片、Base64和本地路径不进入调用日志, so that 性能分析不会扩大照片暴露面。
20. As a 网络较慢的用户, I want 上传图片有严格大小预算, so that 请求不会因为不必要的大图而长时间阻塞。
21. As a 产品负责人, I want 查看端到端P50和P95而不是只有模型调用时长, so that 我能判断用户真实体验是否改善。
22. As a 产品负责人, I want 区分资源加载、图片准备、请求编码、网络模型和校验耗时, so that 优化投资有明确依据。
23. As a 产品负责人, I want 识别质量与旧管线进行固定样本对比, so that 提速不会以明显降低计划质量为代价。
24. As a 产品负责人, I want 新图片管线和流式Runtime独立灰度, so that 指标变化能够归因到单一改动。
25. As a 产品负责人, I want 任一发布门槛失败时停止扩大灰度, so that 性能优化不会损害稳定性和用户信任。
26. As a 开发者, I want 页面只依赖一条图片计划生成管线, so that 拍照和相册不会继续演化出重复逻辑。
27. As a 开发者, I want 图片准备产物具有尺寸、字节数、质量层级和来源元数据, so that 传输和性能决策不再依赖裸Data猜测。
28. As a 开发者, I want Provider Capability由显式配置确定, so that 网络行为可预测、可测试并且没有隐形探测费用。
29. As a 开发者, I want 流式增量停留在Runtime边界, so that Recipe、Artifact和业务页面不绑定供应商协议。
30. As a 开发者, I want 历史Invocation在Schema V19迁移后保留且新增字段为空, so that 缺失数据不会被误解为零耗时。
31. As a 开发者, I want 取消能够传播到图片准备、上传和流式读取, so that 后台没有孤儿任务或取消后继续计费。
32. As a QA工程师, I want 使用脱敏的固定图片评测集重复比较新旧管线, so that 性能和质量回归可以稳定复现。
33. As a QA工程师, I want 在可控延迟的Mock Transport上验证阶段事件, so that 测试不依赖真实模型速度或费用。
34. As a QA工程师, I want 验证超大图、旋转图、低光图、小字图和多图输入, so that 常见相机与相册边界都被覆盖。
35. As a 运维与支持人员, I want 调用记录显示安全的性能指标和失败阶段, so that 我能定位问题而无需查看用户照片或Prompt。
36. As a 无障碍用户, I want 生成阶段和超时提示可以被辅助技术感知, so that 我不依赖动画或颜色判断当前状态。

## Implementation Decisions

- 产品与领域统一使用“图片计划 Recipe”和“Practice Draft”。现场拍照与相册选图是同一Recipe的两个来源，不创建第二套业务能力。
- 新增一条最高业务边界的图片计划生成管线。页面向该管线提交用户选择的图片来源，管线负责来源加载、图片准备、会话重用、Recipe执行、阶段事件、取消传播和端到端性能记录，并返回已经通过Artifact和领域校验的Practice Draft。
- 页面不再负责JPEG策略，也不直接组装模型请求。现有强制预览、Host Approval、防重写入与Invocation关联保持不变。
- 引入会话级 `PreparedImageAsset` 概念，包含调用级资源身份、JPEG字节、像素尺寸、字节数、质量层级、来源类型和内容指纹。它只存在于当前生成会话，不写入SwiftData，不记录绝对路径，不进入长期缓存。
- 相机和相册统一进入后台图片准备服务。原图只解码一次；处理过程修正方向、缩放并编码一次。UI主线程只接收阶段变化和最终结果，不执行图片解码、绘制或JPEG编码。
- 相册最多接收三张图片。资源加载允许有限并发，但同时保留的原始解码对象必须受内存预算约束；输出顺序保持用户选择顺序。
- 默认图片最长边为1024，JPEG初始质量在0.65至0.7之间。Apple Vision快速文字区域检测只评估文字密度和最小区域高度，不识别文本内容；检测到密集小字时使用1280高清可读模式。检测预算为150ms，超时回退1024标准模式。
- 单张会话级派生图片目标不超过1MB，三张合计目标不超过2.5MB。超限时逐级降低JPEG质量，但不低于0.55；仍超限则停止调用模型并请求用户减少图片或重新拍摄。
- 同一生成页面重新生成时复用会话级派生图片。用户关闭、明确取消、内存告警或页面生命周期结束时释放全部派生图片。取消向图片准备、网络上传和流式读取传播。
- 明显无法读取的来源在模型请求前给出重拍建议。标准请求证据不足时不自动发起第二次模型调用；用户可以显式选择高清重试，且该动作产生新的Invocation。
- 生成状态使用事实阶段：准备图片、上传并请求识别、AI生成Practice Draft、校验结果、预览。移除模拟百分比和基于固定时间的“已识别和弦”等文案。超过8秒显示仍在处理与取消入口；超过参考P95提示当前模型响应较慢。
- `ProviderCapabilities`由“用户显式配置、已知Provider/模型配置、保守默认值”的优先级解析。能力至少包含流式、JSON响应格式、图片细节、Prompt缓存和最大图片数。不得通过额外网络请求探测能力，也不得在兼容性失败后静默改变长期配置。
- 支持流式的Provider使用URLSession字节流接收SSE。MessagesRuntime发出首事件和模型增量；UI只消费阶段与首事件，不解析或展示局部JSON。Runtime累积完整输出，完整内容继续经过既有Artifact与领域校验。
- 不支持流式的Provider继续使用完整响应路径。流式中断、网络失败、超时或格式错误均不自动再次调用模型；用户主动重试时，如果仍在同一页面，可以复用会话级派生图片。
- 请求仍通过现有MessagesRuntime和Provider-neutral Transport执行，不绑定Agent SDK。Provider专用参数只能存在于能力适配层，不能进入Recipe、Artifact或页面。
- Schema V19扩展Invocation可观测性，新增字段全部可选：来源加载、图片准备、请求编码、网络与模型、校验、端到端用户等待、源字节数、派生字节数、图片数和流式首事件耗时。迁移后的历史记录保持空值，不将未采集数据写为零。
- 性能计时使用单调时钟采集，持久化为毫秒数。日志只记录安全数值、Recipe版本、Runtime、模型安全标识和能力配置标识；禁止记录照片、Base64、Prompt正文、完整响应、API Key、私有接口地址和绝对路径。
- 性能验收分两层。App可控阶段以iPhone 13/A15级真机和单张12MP照片为基线，图片准备P95不超过800ms，主线程不得出现超过250ms的处理卡顿。端到端测试固定参考视觉模型、正常Wi-Fi和约80ms网络往返。
- 单图到预览目标为P50不超过6秒、P95不超过12秒；三图目标为P50不超过9秒、P95不超过18秒。BYOK和自定义接口展示实测结果，不承诺统一Provider SLA。
- 建立至少40张脱敏固定评测集，覆盖和弦图、六线谱或曲谱、手写练习清单、低光倾斜与小字困难样本。评测标题、分类、和弦、步骤和时长约束；结构合法率不得下降，核心字段准确率相对旧管线下降不得超过3个百分点。
- 新图片准备管线和Runtime流式能力使用两个独立功能开关。发布按内部、10%、50%、全量推进；任何性能、质量、安全或失败率门槛不达标时停止扩大灰度，并可独立回退到旧图片管线或完整响应Runtime。
- AI失败率不得比旧管线高2个百分点以上。取消后继续请求、图片持久化、路径泄漏或未经批准写入均为零容忍发布阻断项。

## Testing Decisions

- 主要行为测试只通过最高业务缝“图片计划生成管线”观察外部行为：输入图片来源与Provider能力，观察阶段事件、Prepared Image统计、Transport请求、取消结果、性能记录及最终Practice Draft。测试不检查内部调用顺序或私有方法。
- 该最高业务缝使用可控图片Fixture、确定性时钟和可编程Mock Transport，覆盖成功、慢响应、流式首事件、非流式回退、网络失败、取消、证据不足、用户高清重试和重新生成复用。它是本功能最重要的回归测试边界。
- 图片准备契约测试覆盖方向修正、1024/1280选择、文字检测超时、质量逐级调整、单图与总字节上限、选择顺序、内容指纹、内存告警释放和取消。测试验证输出行为，不锁定具体UIKit绘制步骤。
- Transport契约测试覆盖SSE分片、跨分片JSON事件、首事件时间、完整内容累计、取消、Provider不支持流式、JSON响应格式能力关闭，以及失败时不得自动发送第二次请求。
- Recipe与Artifact测试复用现有 `GitaPracticeExtensionTests` 和图片计划Fixture，验证Prepared Image仍形成调用级资源、Snapshot与SeenSet一致、非法Artifact被拒绝、Practice Draft仍需预览和Host Approval。
- 页面状态测试复用 `PhotoPracticeDraftLifecycle` 先例，验证事实阶段、超过8秒提示、超过参考P95提示、取消入口、辅助技术播报、重新生成与关闭页面清理。不得依赖动画帧或模拟百分比。
- Schema迁移测试从V18 Fixture迁移至V19，验证历史Invocation保留、新字段为空、数值字段可写入和读取、Debug输出脱敏。未采集不能等同于零。
- 安全测试验证日志与持久化存储中不存在JPEG魔数、Base64前缀、原图字节、本地路径、Prompt正文、完整Provider响应、API Key和私有Base URL。
- 性能测试在iPhone 13/A15级真机执行单张12MP照片和三张照片用例，分别采集来源加载、图片准备、请求编码与主线程卡顿；Mock Transport隔离App可控预算，参考Provider测试端到端目标。
- 质量测试对40张固定评测集运行旧管线与新管线，比较结构合法率和五类核心字段。困难样本允许输出证据不足或请求重拍，不把拒绝当作准确识别失败。
- 灰度验收持续比较P50/P95、失败率、取消率、高清重试率、派生字节数和Practice Draft接受率。新旧功能开关必须支持独立回滚演练。
- 现有测试先例包括 `ImageStepGeneratorTests`、`GitaPracticeExtensionTests`、`MessagesRuntimeTests`、`AITransportTests`、`AIInvocationStoreTests` 和 `PhotoPracticeDraftLifecycle` 测试；只有最高业务缝缺失时才新增协议，不为每个内部类建立独立Mock层。

## Out of Scope

- 不绑定OpenAI或其他厂商的Agent SDK。
- 不实现Agent SDK Runtime、Managed Agents或多Agent编排。
- 不增加服务端图片存储、图片CDN或跨设备派生图片缓存。
- 不把本地文字区域检测扩展为面向用户的完整OCR功能。
- 不展示未经完整Artifact校验的局部JSON或半成品Practice Draft。
- 不修改Practice Draft预览、Host Approval、防重写入和PracticeItem业务门禁。
- 不修改媒体复盘、音频波形和视频诊断管线。
- 不引入自动多模型竞速、自动高分辨率二次调用或后台隐形重试。
- 不为了Prompt Cache长期保存用户照片；Prompt Cache不是本次图片场景的主要加速手段。
- 不承诺所有BYOK或自定义Provider满足统一端到端SLA。
- 不在本次重构练习业务模型、Candidate Memory或其他AI Recipe。

## Further Notes

- 当前拍照路径存在两次JPEG编码：相机回调先将原始UIImage编码为高质量JPEG，图片生成器随后再次解码、缩放并编码。新管线必须消除这一重复工作。
- 当前图片压缩发生在MainActor隔离的生成器中；新管线必须用测试证明主线程不再承担解码、缩放或JPEG编码。
- 当前图片通过Base64嵌入Chat Completions JSON。第一阶段保留该协议，但以派生字节预算降低上传成本；改用文件上传或对象存储属于未来独立决策。
- 当前进度根据固定时间推进并停在90%，不能用于性能诊断。上线新管线后，应删除或停用模拟进度实现。
- 当前已启动测试模拟器没有可用的AI Invocation样本，因此开发第一阶段必须先补可观测性，再以真实调用建立基线。
- `CONTEXT.md` 已增加“图片计划 Recipe”和“会话级派生图片”定义。相关实现和文案必须使用该项目语言。
- 本规格遵守现有ADR：四个AI Recipe独立迁移；图片计划生成的Practice Draft必须经过预览和Host Approval；AI派生数据不能越过既有安全与写入边界。
